# Query Performance Review – Student Training Portal

## 1. Objective

The objective of this review was to inspect important Django QuerySets, understand the generated SQL queries, and verify the use of ORM optimization techniques.

The review focused on:
- Identifying database JOIN operations.
- Understanding filtering and ordering conditions.
- Verifying `select_related()` and `prefetch_related()`.
- Checking selected columns using `values()`.
- Understanding how Django ORM translates QuerySets into SQL.

## 2. SQL Query Inspection

### Query 1: Base Students QuerySet

**QuerySet:**
```python
base_students = base_students.select_related(
    'department',
    'user'
).prefetch_related('courses')
```

**SQL Inspection:**

Generated SQL included:
- `student_app_student` as the main table.
- `LEFT OUTER JOIN` with `auth_user`.
- `LEFT OUTER JOIN` with `student_app_department`.

**Observation:**

`select_related()` fetches the related User and Department records through SQL JOIN operations.

`prefetch_related('courses')` fetches related courses using a separate query when the QuerySet is evaluated.

### Query 2: Active Students QuerySet

**QuerySet:**
```python
active_students = base_students.filter(
    is_active=True
).order_by('-id')
```

**SQL Inspection:**

The generated SQL included:

```sql
WHERE student_app_student.is_active = True
ORDER BY student_app_student.id DESC
```

**Observation:**

The database retrieves only active student records and orders them by descending ID.

The existing User and Department JOIN operations are also maintained.

### Query 3: Filtered Students QuerySet

**Filters inspected:**
- Department filter
- Course filter
- Active status filter
- Search and other available filters

**SQL Inspection:**

The generated SQL included:
- `INNER JOIN` with the Department table.
- `INNER JOIN` with the ManyToMany intermediate table `student_app_student_courses`.
- `WHERE` conditions for department, course and active status.
- `ORDER BY` student ID in descending order.

**Observation:**

Django ORM generates the required JOIN operations when filtering students using related Department and Course fields.

The SQL conditions change according to the filters selected by the user.

### Query 4: Departments QuerySet

**QuerySet:**
```python
Department.objects.values('id', 'name')
```

**SQL Inspection:**

```sql
SELECT
    student_app_department.id AS id,
    student_app_department.name AS name
FROM student_app_department;
```

**Observation:**

Only the required `id` and `name` columns are fetched instead of retrieving all Department model fields.

Using `values()` is appropriate for displaying department information in dropdowns.

### Query 5: Courses QuerySet

**QuerySet:**
```python
Course.objects.values('id', 'course_name', 'code')
```

**SQL Inspection:**

```sql
SELECT
    student_app_course.id AS id,
    student_app_course.course_name AS course_name,
    student_app_course.code AS code
FROM student_app_course;
```

**Observation:**

Only the required course fields are retrieved.

Using `values()` avoids fetching unnecessary model fields when only selected course information is needed.

## 3. Overall Observations

- `select_related()` generates SQL JOIN operations for ForeignKey and OneToOne relationships.
- `prefetch_related()` retrieves ManyToMany and reverse-related records through separate queries.
- Filtering conditions are translated into SQL `WHERE` clauses.
- Ordering is handled through SQL `ORDER BY`.
- `values()` retrieves only the selected columns.
- Different filter combinations generate different SQL queries.

## 4. Conclusion

Inspected five important QuerySets from the Student List view to understand the SQL generated by Django ORM.

The inspection helped verify relationship loading, filtering, ordering, and selected-column retrieval.

The existing QuerySet optimizations were reviewed to improve database query efficiency and reduce unnecessary data retrieval.
